01

The brief

Design and build one complete web application. The topic is yours; the standard is a working product that a real user can operate — not a set of disconnected features.

This is the only project in COMP3421. Working alone or in a pair, you will take an idea from concept to a running web application, then demonstrate and defend it. You will use the stack taught in the course — HTML, CSS and JavaScript on the client, plus a server and a database for pairs (optional for solo) — and the workflow used in lectures and labs. You will design the architecture, build and test the app, and deploy it if claiming the +5 deployment bonus. You may choose any topic, any platform and any framework or library. Vibe coding is allowed; hand-coding earns a bonus (page 3). Two-person groups must build both sides and a database; a solo project may omit the server, but server-side marks are then unavailable.

Why this project

AI can generate code in seconds. What it cannot do for you is decide what to build, structure the system, judge whether the result is correct and secure, or explain the trade-offs. That is what this project assesses.

What you will deliver

Client

Front end

A responsive, multi-view interface with real interaction, form validation and no broken flows.

Logic

Back end

Application logic and data access behind an API — validation, errors, state changes and persistence.

Data

Database

A persistent store with a schema and seed data. Required for two-person groups.

Bonus

Deployment

A public URL on a cloud host or the department server. Up to +5 bonus marks.

Two bonus opportunities: real deployment +5 · hand-coded implementation +5 (no AI-generated code). Maximum project score: 110.

The one hard rule

It must be a code-based web application — not a static brochure site, and not a site assembled with a CMS or website builder such as WordPress, Wix, Squarespace or Shopify. If a visitor can only read pages, or the site is configured rather than built, the brief is not met.

02

What to build

A complete application, not a collection of screens. The baseline defines “complete”; marks above it come from quality, depth and finish.

Client side

Front end

  • 3+ functional views (pairs: 6+).
  • Responsive from phone to desktop.
  • Semantic HTML, CSS layout (Grid/Flexbox).
  • JavaScript interactivity and form validation.
  • Labels, alt text, keyboard access; no console errors.
Server side

Back end

  • Application logic behind an API.
  • Validate every input on the server.
  • Handle errors and return JSON.
  • Auth and authorisation for protected actions (recommended).
  • Any server platform is allowed.
Data

Database

  • A real database: SQLite, MySQL, PostgreSQL, MongoDB or a managed service.
  • Schema and seed data included.
  • Reads and writes persist across restarts.
  • No secrets or real personal data.

What counts as complete

A new user can finish the main task end-to-end: the data is saved, invalid input is handled, and the app still works after a refresh. A template with your logo, hard-coded sample data, or buttons that do nothing is not complete.

Technology rules

Any stack is allowed — any framework, library, database and hosting platform. The course teaches HTML/CSS/JavaScript + Node.js/Express, so that is the best-supported path. The rule is simple: your TA must be able to run your app by following README.md, and you must be able to explain and defend the core application logic.

Milestones & deliverables

Three checkpoints. The outline gets you feedback, the submission is what is marked, and the demo is where you prove it runs.

Week 8 · 5%

Project outline

One-page PDF via Blackboard: group, title, abstract, scope, stack, data model sketch and roles.

Week 13 · 75%

Final submission

One zip per member: report, signed contribution declaration, ai-use.md, source code, README, schema and seed data.

Week 14–15 · 20%

Presentation & demo

5–8 minutes: overview, live or recorded demo, and Q&A. All members present.

Percentages are shares of the 100 project marks. +5 deployment and +5 hand-coding bonus before the demo; exact dates are on Blackboard.

3.1 Project outline — 5%

Due: end of Week 8, via Blackboard. File: COMP3421_Outline_<GroupID>.pdf.

  • Members: names, student IDs and tutorial group; solo or pair.
  • Title + abstract (150–250 words): problem, target users, what the app does.
  • MVP features and optional stretch features.
  • Stack: client; server and database (pairs) or client-side storage (solo); deployment plan (optional, +5).
  • Data entities: 2–5 main things the app stores and how they relate (solo: 2+; pairs: 3+).
  • Roles and provisional contribution split; risks and what you will cut.

The outline is only 5%, but it is your chance to get early feedback. Submit it even if the idea is still moving. If the scope changes substantially, email the instructor and your TA.

3.2 Final submission — 75%

Due: end of Week 13, via Blackboard. One joint report per group. Each member submits the package separately on Blackboard; the two submissions may overlap in content. Do not include node_modules/, .env files or generated files. Provide test accounts and seed data. Every group submits contribution-declaration.pdf: pairs sign the joint statement; a solo student signs only the Solo Project Statement.

README must cover: prerequisites, install, environment variables, database setup, run, test accounts, deployment URL and known limitations.

Report must include
  • Cover; abstract and introduction; requirements and feature list.
  • Architecture: diagram, stack, components and their responsibilities.
  • Data model and API: ERD plus an endpoint table (method, input, output, status).
  • Implementation: key flows, non-trivial decisions and code highlights.
  • UI/UX: screenshots and evidence of responsive behaviour.
  • Testing: plan, cases, results and known bugs.
  • Deployment and operations; limitations and future work.
  • Individual contributions; references; appendix (user manual, AI use, third-party assets).

Suggested length: 10–15 pages (pair) or 7–10 (solo), excluding appendices. Marks are for content, not length.

3.3 Presentation & demonstration — 20%

  • 5–8 minutes per group, plus Q&A. All group members present and speak.
  • Live or recorded demo — a recording is acceptable if it shows the actual submitted build and you can answer questions live.
  • Demo the submitted build, from the submitted package — not a private “demo version”.
  • Prepare seeded data and test accounts. Show persistence: reload and re-open the app.
  • Have a backup: screen recording, screenshots and a local fallback. Do not rely on the cloud during the demo.
  • No live coding. A short code walkthrough may form part of the Q&A; show, don’t tell; be ready to explain your code and data.

How you are assessed

Your project is marked out of 100 using the marking sheet in Appendix A, then weighted to 10% of your subject grade. Creative work involves judgement; the criteria and band descriptors make that judgement consistent and transparent.

ComponentMarksWhat it rewards
Project outline5A clear, feasible plan, submitted on time, with members and roles defined.
Functionality & implementation50A working application: logic, features, architecture, client, server/data, robustness.
Project report25Design documentation, data model, testing evidence, user manual and signed contribution declaration.
Demonstration20A clear 5–8-minute presentation, a live or recorded demo without runtime errors, and confident answers.
Real deployment+5A publicly reachable, stable deployment of the submitted build, documented in the README.
Hand-coded implementation+5Source code written by the team, with no AI-generated code; verified by declaration and code walkthrough.

The project is worth 10% of COMP3421. Its base is 100 marks, scaled to that 10% weight; bonus marks (max +10) are added to the project score, which can reach 110. The other 90% is the final exam (70%), mid-term (10%) and assignments (10%).

How markers judge quality

Four dimensions run through every component. They are not separate scores; they are the lens markers use when reading the rubric on the next page.

Complexity & scope

How ambitious and difficult the problem is, and how much of it you completed. Judged by interacting parts, not page count.

Aesthetics & usability

Visual hierarchy, consistency, responsiveness, accessibility, feedback and empty/error states. A calm, clear interface beats decoration.

Maturity

Does it work end-to-end under realistic use? Validation, error handling, persistence, reproducible setup, security basics.

Technique

Appropriate use of course concepts, clean architecture, code quality, and evidence of testing and deployment.

Group work, integrity & AI

A pair can achieve more than a solo project — but only if the work is genuinely shared and each of you can stand behind the whole system.

Working in a pair

  • Agree roles on day one: front-end lead and back-end lead. Ownership is clear, but both of you integrate, test and review the whole app.
  • Keep one shared Git repository. Commit often with meaningful messages; the history is evidence of contribution.
  • Write one joint report. Divide sections, review each other’s writing, and state who wrote what.
  • All group members attend the demo and can run the app from a clean install.
  • If contribution becomes uneven, tell your TA and the instructor early — not after Week 13.

The report and the contribution declaration

Required for every group

Submit a signed Contribution Declaration (Appendix B, contribution-declaration.pdf) and summarise it in the report. It records each member’s role, components owned, evidence (files/commits), percentage of total work, and the report sections they wrote. Percentages must sum to 100% and match the evidence. Pairs complete the joint statement; solo students complete only the Solo Project Statement. Each member submits the package separately; the same report and code may be submitted by both.

  • One joint report for the pair. It must contain a short “Individual contributions” section, and the signed declaration must be attached as a separate PDF.
  • The group mark is the starting point. Individual marks may be adjusted up or down for contribution, demonstrated understanding and the demo. In serious cases, a member may receive a mark that reflects only their verified contribution.
  • Free-riding is not a strategy: if you cannot explain code you submitted, it affects your individual mark.

Academic integrity

  • Your design, code and writing must be created for this project. Declared AI assistance is permitted under the rules below; you may discuss ideas with classmates, but do not share code, reports or assets.
  • Do not resubmit a previous course project, a lab solution, or another group’s work. Small snippets from lectures and labs may be reused with attribution — not wholesale.
  • Cite libraries, frameworks, templates, images, icons and fonts; use licensed or public-domain assets and keep the licence information where required.
  • Plagiarism, undeclared AI assistance and fabricated contribution claims may be treated as academic misconduct under University regulations.

AI tools and the hand-coding bonus

Vibe coding route

AI tools may generate code. Declare the tool and version, what it was used for, which files or parts it produced, and how you verified it. You remain responsible for every line. You are eligible for all marks except the hand-coding bonus.

Hand-coding route

You write the application code yourself. AI may explain concepts, debug or review, but must not generate submitted code. Declare any AI use and claim the bonus in ai-use.md and the contribution declaration. Verified by a code walkthrough.

If AI-generated code is found in a project claiming the hand-coding bonus, the bonus is withdrawn. The project itself is still assessed — under the vibe-coding route. A knowingly false hand-coding declaration may also be handled under the University’s academic integrity procedures. The final exam rules are unchanged: no electronic devices or AI tools in the exam.

Data, third-party assets & safety

  • Use dummy data, never real personal data, passwords or payment details.
  • Keep API keys out of the repository; ship .env.example, never .env.
  • No illegal, harmful or harassing content; follow PolyU IT policies and the law.
  • Validate and sanitise user input; protect write operations.

Support & FAQ

Ask early. A short question in Week 9 is worth more than a crisis in Week 13.

Frequently asked questions

Do we have to use Node.js and Express?
No. Any platform, framework and library is allowed. The course teaches Node.js/Express, so it is the best-supported path, but your TA must be able to run your app from your README.
Can we use React, Vue, Bootstrap, Tailwind or a template?
Yes — declare them and their licences. Frameworks and templates do not earn marks by themselves; what you build, integrate and customise does.
Can we use WordPress, Wix or Shopify?
No. CMS and website-builder platforms are not permitted; the project must be built in code. Code-based frameworks are fine; a static-site generator may be used as a build tool, but the result must still be an interactive app with data and logic.
Can we use Firebase, Supabase or another managed backend?
Yes, as part of your stack. Declare the service and show how it is used. Server-side marks are based on the application logic and data design you build, not on the hosting brand.
Can we use AI / vibe coding?
Yes, with a declaration. If you want the +5 hand-coding bonus, AI must not generate any submitted code — it may only explain, debug or review.
Can our project be a static website or portfolio?
No. It must be an interactive web application with data and logic. A portfolio with accounts and dynamic content could qualify; a set of static pages does not.

Before you submit

  • Group of 1–2 confirmed; roles and contribution plan agreed.
  • Outline submitted on Blackboard by the end of Week 8.
  • Topic is an interactive web application, not a CMS site.
  • Coding route declared: vibe coding or hand-coding.
  • Client and server (if used) run from a clean install following README.
  • Database schema and seed data included (if used); test accounts work.
  • Contribution declaration / solo statement signed and attached; report has the contributions section.
  • AI use and third-party assets declared with licences.
  • Responsive check at 360 px and desktop; no console errors.
  • Backup demo video and screenshots ready.
  • Zip opens; no node_modules or .env; filename correct.
  • Each member of a two-person group submitted the package separately (content may overlap); deadline met.

More questions

Can we change the topic after Week 8?
Yes. Email the instructor and TA; a major change may need a short updated outline. Your outline mark is based on what you submitted.
What if our deployment is down during the demo?
Demo a local build from the submitted package. The demo must not depend on the cloud; the deployment bonus is judged on evidence and stability.
How many features or pages do we need?
No fixed number. The baseline on page 3 defines “complete”. A smaller app that is finished, polished and tested scores better than a large one with broken features.
What if my partner does not contribute?
Raise it early with your TA and the instructor. The contribution declaration and demo are used to adjust individual marks; do not wait until the deadline.
Can we submit late?
Follow the subject’s late-submission policy and tell the instructor as soon as possible. Do not assume an extension.
